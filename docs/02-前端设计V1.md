## 一、设计基调

### 1.1 参考裁定

用户提供 3 张参考图，最终裁定：

| 参考 | 特征 | 裁定 |
|---|---|---|
| 图一（校园二手 · 拼多多式） | 类目图标墙 + 双列瀑布流 + 5 tab 底栏 + 红色价格 + 多色图标 | ❌ **否定** |
| 图二（IIT Kanpur） | 单一 teal 主色、底栏仅 3 格（BUY / 头像 / SELL）、全屏品牌色个人页 | ✅ 认可 |
| 图三（CIT Marketplace） | 大圆角图片卡、图上叠加地点与价格胶囊、语义分区 + See All | ✅ 认可 |

**目标调性一句话：克制的校园工具感 —— 单一主色、大留白、价格是唯一强调色。**

### 1.2 七条禁止（来自图一的教训）

| # | 禁止 | 原因 |
|---|---|---|
| 1 | 首页顶部放彩色类目图标墙 | 挤占首屏，「廉价感」第一来源 |
| 2 | 顶部超过 2 层结构 | 用户第一眼不知道看哪 |
| 3 | 出现第二种高饱和色 | 主色失焦 |
| 4 | 卡片内超过 3 层信息 | 层级扁平 = 全都一样响 |
| 5 | 商品图比例不统一 | 瀑布流参差 |
| 6 | 促销语言（省钱券 / 积分抵钱 / 限时秒杀） | 与校园闲置的定位冲突 |
| 7 | 底部 tab 超过 3 个 | 无内容可填的 tab 稀释核心动作 |

### 1.3 八条必须（来自图二 / 图三的经验）

| 维度 | 规范 |
|---|---|
| 主色 | **只允许 1 个主色** + 4 级中性灰；主色只出现在价格、主按钮、选中态 |
| 顶部 | 最多 2 层：① 身份 / 标题层 ② 搜索层 |
| 价格 | 主色大字，独占视觉焦点；其余信息灰色小字 |
| 卡片 | 大圆角 + 柔和阴影；图片统一比例 |
| 组织 | 语义分区 + 「查看全部」，不做无限瀑布流 |
| **图上叠加** | 交易地点、价格做成胶囊标签叠在图上（图三的核心手法，同时解决「信息全」与「版面干净」） |
| 底栏 | **3 格**：首页 / 发布 / 我的 |
| 校园归属感 | 顶部显示昵称 + 学校 / 校区；卖家主页显示院系 |

### 1.4 落地参数

- **画布**：375 × 812（iPhone X 基准），底部安全区预留 34px
- **间距基准**：8px；页面左右边距 16px；卡片之间 12px
- **圆角**：卡片 12–16px ／ 按钮 8–10px ／ 胶囊标签 999px
- **阴影**：`0 2px 8px rgba(0,0,0,.06)`（浅而宽，禁用深阴影）
- **字号：只允许 4 档** —— 这是「层级清晰」的关键

| 用途 | 字号 | 字重 |
|---|---|---|
| 价格 / 页面主标题 | 20–22px | 600 |
| 卡片标题 / 区块标题 | 16px | 500–600 |
| 正文 / 商品描述 | 14px | 400 |
| 辅助信息（时间、地点、浏览量） | 12px | 400 |

- **语义色**：成功=绿、待处理=橙、失败/驳回=红、失效=灰。**只用于状态标签，不用于大面积填充**
- **图片**：列表封面 1:1，详情轮播 1:1 或 4:3，**统一裁切，不做原图直出**

### 1.5 三条本项目差异化设计点

| # | 设计点 | 说明 |
|---|---|---|
| 1 | **交易地点当主视觉元素** | 只支持校内当面自提，`trade_place` 必填。卡片与详情页都要给它独立视觉位（胶囊标签），发布时用校园地标枚举下拉，不做自由输入 |
| 2 | **CTA 语义避开「支付」** | 无购物车、无在线支付。主按钮是「我想要 / 联系卖家」；付款按钮文案必须是「**我已完成线下付款**」 |
| 3 | **审核状态必须可见** | 商品有 `PENDING_AUDIT` / `REJECTED`，卖家须在「我的发布」看到「审核中 / 已驳回 + 驳回理由」 |

## 二、页面地图

用户端共 **14 个页面**（`01-总体设计V1.md` §十三 原有 10 个 + 本轮新增 4 个）。

### 2.1 页面清单

| # | 页面 | 路由 | 来源 | 后端归属 |
|---|---|---|---|---|
| 1 | 登录 | `/login` | 原有 | user-service |
| 2 | 注册 | `/register` | 原有 | user-service |
| 3 | 首页 | `/` | 原有 | product-service（+ user 批量查卖家） |
| 4 | **商品列表 / 搜索结果** | `/search` | 🆕 新增 | product-service |
| 5 | 商品详情 | `/product/:id` | 原有 | product-service（+ user 查卖家与联系方式） |
| 6 | 发布商品 | `/publish` | 原有 | product-service |
| 7 | 编辑商品 | `/publish/:id` | 原有（复用发布页） | product-service |
| 8 | **个人中心（聚合页）** | `/mine` | 🆕 新增 | 纯前端聚合，无独立接口 |
| 9 | 我的发布 | `/user/products` | 原有 | product-service |
| 10 | 我的订单 | `/user/orders` | 原有 | order-service |
| 11 | 订单详情 | `/order/:orderNo` | 原有 | order-service |
| 12 | 我的收藏 | `/user/favorites` | 原有 | product-service |
| 13 | 个人资料（编辑） | `/user/profile` | 原有 | user-service |
| 14 | **卖家主页** | `/seller/:id` | 🆕 新增 | product-service + user-service |
| 15 | **通知中心** | `/notices` | 🆕 新增 | **无后端**（聚合视图，见 §2.4） |

> 「个人中心」（`/mine`）与「个人资料」（`/user/profile`）是两个不同页面，不要混淆：
> 前者是**入口聚合**（我的发布 / 我的订单 / 我的收藏 / 资料 …），后者是**信息编辑表单**。

### 2.2 导航结构

**底部 tab（3 格，常驻）**

| 位置 | 页面 | 路由 |
|---|---|---|
| 左 | 首页 | `/` |
| 中 | 发布 | `/publish` |
| 右 | 我的 | `/mine` |

其中「发布」建议作为视觉重心（凸起或主色填充），具体形式由设计确定。

**不进底栏的页面**（均为二级页，顶部需带返回）：登录/注册、商品列表、商品详情、发布、卖家主页、我的发布、我的订单、订单详情、我的收藏、个人资料、通知中心。

### 2.3 登录态策略

**不做整站强制登录。** 仅在触发受限动作时拦截。

| 范围 | 游客可访问 | 说明 |
|---|---|---|
| 首页 / 商品列表 / 商品详情 / 卖家主页 | ✅ | 业务口径：浏览不设限 |
| 详情页的「联系方式」 | ❌ | **登录后可见**（方案 A，见 §六） |
| 发布 / 下单 / 收藏 / 我的* / 通知中心 | ❌ | 拦截后跳登录 |

**拦截规则**：弹出登录页而非跳走；登录成功后**原地返回并继续原动作**（例如点收藏 → 登录 → 自动完成收藏）。

### 2.4 设计决策：通知中心不建表

`01-总体设计V1.md` §十五 明确不做站内聊天，也没有通知表。因此**通知中心做成「聚合视图」**：

- 数据来源：从「我的发布」拉取 `PENDING_AUDIT` / `REJECTED` 商品，从「我的订单」拉取待处理订单；
- 前端拼装成列表，**不新增表、不新增接口、不引入跨服务数据归属问题**；
- 代价：只有被动展示，没有推送提醒（可接受，符合「宁可少做」铁律）。

## 三、公共规范

### 3.1 统一响应体（已定，前端按此解析）

来自 `huashui-common` 的 `Result<T>`：

```json
{ "code": 200, "message": "success", "data": {} }
```

- **判断成功的唯一标准是 `code === 200`**，不要依赖 HTTP 状态码。
- 分页数据是 `PageResult<T>`：

```json
{ "total": 120, "pages": 6, "current": 1, "size": 20, "records": [] }
```

- 请求头 `X-User-Id` / `X-User-Role` **由网关注入**，前端不要伪造；前端只需带 `Authorization: Bearer <token>`。

### 3.2 顶部规范

| 页面类型 | 顶部内容 |
|---|---|
| 首页 | 第 1 层：定位/校区 + 通知入口；第 2 层：搜索框 |
| 二级页 | 左返回 + 居中标题（最长 8 字，超出省略） |
| 我的 / 个人中心 | 无返回，第 1 层为头像 + 昵称 + 院系 |

### 3.3 加载 / 空 / 错三态

| 状态 | 要求 |
|---|---|
| 加载中 | **骨架屏**优先，不用整屏转圈（列表页尤其） |
| 空态 | 一句人话 + 一个动作。例：「还没有发布过商品」+「去发布」按钮 |
| 出错 | 展示 `Result.message` 原文（后端已做全局异常处理），不要笼统提示「网络错误」 |
| 加载更多 | 触底加载，到底显示「没有更多了」，不使用页码分页器 |

### 3.4 微信内浏览器兼容

H5 会在微信内被打开，需注意：iOS 底部安全区（`env(safe-area-inset-bottom)`）、微信返回手势与页面内返回按钮的双重返回问题。

## 四、核心页面结构

> 以下只给**区块顺序与元素清单**（骨架），视觉样式由设计确定。

### 4.1 首页 `/`

```
① 顶部：校区/定位 + 通知入口
② 搜索框（点击进入 /search，首页不做即时搜索）
③ 分类胶囊行（横向滚动，不要做成图标墙）
④ 分区一：热门推荐（最多 6 个，右侧「查看全部」）
⑤ 分区二：最新发布（无限触底加载）
```

- 商品卡片字段：**封面图（1:1）+ 交易地点胶囊 + 标题（1 行截断）+ 价格（主色）+ 原价（划线，可无）**
- **卡片不放卖家昵称与头像**（对决策无帮助，图一的问题之一）
- 首屏不放任何运营位（无 banner、无优惠券、无签到）

### 4.2 商品列表 / 搜索结果 `/search`

参数：`?kw=` 或 `?categoryId=` 或 `?campus=`（可组合）

```
① 顶部返回 + 搜索框（可改词）
② 筛选行：排序（最新 / 价格↑ / 价格↓ / 最多浏览）+ 校区筛选 + 成色筛选
③ 结果双列栅格（1:1 封面，与首页卡片一致）
```

- 筛选用**胶囊 chip**，不用下拉菜单
- 结果为空时给「换个词试试」而不是空白页

### 4.3 商品详情 `/product/:id`

```
① 图片轮播（1:1，最多 9 张）+ 状态角标（已售出 / 已下架）
② 价格区：售价（主色大字）+ 原价（划线）+ 浏览/收藏数
③ 标题 + 成色 + 分类
④ 交易地点卡（独立区块，胶囊 + 「校内当面自提」说明）
⑤ 商品描述
⑥ 卖家卡：头像 + 昵称 + 院系 + 历史成交笔数 → 点击进 /seller/:id
⑦ 「联系卖家」按钮（登录后可见手机号 + 一键复制，见 §六）
⑧ 底部固定操作条：收藏（心形）+ 主按钮「我想要」/「已售出」（禁用态）
```

**关键规则**：
- 主按钮文案随商品状态变化，见 §五
- 已售出 / 已下架商品仍可访问（不 404），但主按钮禁用并显示原因
- 商品描述里的换行要保留（`white-space: pre-wrap`）

### 4.4 发布 / 编辑商品 `/publish`、`/publish/:id`

```
① 图片上传（1–9 张，首图为封面，可拖拽排序）
② 标题（必填，≤ 30 字，带计数）
③ 描述（必填，≤ 500 字）
④ 分类（必选，来自 /api/category/list）
⑤ 价格（必填）+ 原价（选填，用于划线展示）
⑥ 成色（必选：全新 / 九成新 / 七成新 / 五成新及以下）
⑦ 交易地点（必选，两级联动：校区 → 地标，见 §八）
⑧ 提交按钮（固定底部）
```

- 编辑态复用同一页面，回填数据；被驳回的商品在此修改后重新提交（状态回到 `PENDING_AUDIT`）
- 提交成功后给明确反馈：「已提交，等待审核」——**不要提示「发布成功」**，因为还要审核

> ✅ **成色字段已落地**（2026-09-26）：`t_product.condition_level TINYINT NOT NULL DEFAULT 1`，
> 已通过 `ALTER TABLE` 应用到 `huashui_product`，建表脚本 `docs/sql/02-product.sql` 已同步更新。

### 4.5 个人中心 `/mine`

```
① 顶部：头像 + 昵称 + 院系 + （保留：学校名）
② 数据条：在售 N ｜ 已售出 N ｜ 收藏 N（点击分别跳转）
③ 菜单组一：我的发布 / 我的订单 / 我的收藏
④ 菜单组二：通知中心（带红点数）/ 个人资料 / 退出登录
```

### 4.6 我的发布 `/user/products`

Tab 分组（**按商品状态分**）：

| Tab | 包含状态 | 可操作 |
|---|---|---|
| 在售 | `ON_SALE` | 编辑 / 下架 |
| 审核中 | `PENDING_AUDIT` | 编辑 |
| 已驳回 | `REJECTED` | **显示驳回理由** + 编辑后重提 |
| 已锁定 | `LOCKED` | 查看订单 |
| 已售出 / 已下架 | `SOLD` / `OFF_SHELF` | 已下架可「重新上架」 |

### 4.7 我的订单 `/user/orders`

两个视角 Tab（`t_orders` 有 `buyer_id` 与 `seller_id`，同一账号两个身份）：

| Tab | 查询条件 | 说明 |
|---|---|---|
| 我买到的 | `buyer_id = 当前用户` | 展示卖家信息 + 交易地点 |
| 我卖出的 | `seller_id = 当前用户` | 展示买家信息 + 联系方式 |

**订单详情 `/order/:orderNo`** 是本项目交互最重的页面：

```
① 状态条（大字状态 + 倒计时）
② 商品快照卡（封面 + 标题 + 成交价）—— 注意用订单快照，不要再去查商品
③ 交易信息：交易地点 / 联系方式 / 下单时间 / 订单号
④ 主操作按钮（随状态变化，见 §五）
```

**必须实现：待支付倒计时。** 后端 `t_orders.close_deadline` 已给出截止时间（默认 30 分钟），前端显示剩余时间，归零后刷新状态（订单会被 XXL-JOB 取消）。

## 五、状态 → 前端展示映射

> ✅ **状态码口径已核实**（2026-09-26 直接查库确认）：**`TINYINT` + `Integer` 枚举，前端一律按数字解析。**
> - `huashui_product.t_product.status` = `tinyint NOT NULL DEFAULT 0`，注释「0 待审核，1 在售，2 已锁定，3 已售出，4 已下架，5 已驳回」
> - `huashui_order.t_orders.status` = `tinyint NOT NULL DEFAULT 0`
> - 两者与 `huashui-common` 的 `ProductStatus` / `OrderStatus` 枚举定义**完全一致**
>
> `01-总体设计V1.md` §八 示例 SQL 里的 `status = 'ON_SALE'` 是**伪代码**，不是真实字段值，无需修改。
> 建议后端返回时同时给出 `status`（数字）与 `statusDesc`（中文），前端不用自己维护映射表。

### 5.1 商品状态

| 状态 | code | 前端展示 | 详情页主按钮 | 他人可见 |
|---|---|---|---|---|
| 待审核 | 0 | 橙色标签「审核中」 | — | ❌ 仅卖家自己可见 |
| 在售 | 1 | 无标签（默认态） | 「我想要」 | ✅ |
| 已锁定 | 2 | 橙色「已被锁定」 | 「已被抢购」（禁用） | ✅ |
| 已售出 | 3 | 灰色角标「已售出」 | 「已售出」（禁用） | ✅ |
| 已下架 | 4 | 灰色角标「已下架」 | 「已下架」（禁用） | ✅ |
| 已驳回 | 5 | 红色标签「已驳回」+ 理由 | — | ❌ 仅卖家自己可见 |

**规则**：列表页只展示 `ON_SALE` 的商品（加上卖家自己视角的 `LOCKED`）。`PENDING_AUDIT` 与 `REJECTED` 只在「我的发布」可见。

### 5.2 订单状态

| 状态 | code | 状态文案 | 主按钮（买家） | 主按钮（卖家） |
|---|---|---|---|---|
| 待支付 | 0 | 「待付款」+ 倒计时 | **我已完成线下付款** / 取消订单 | 等待买家付款 |
| 已付款 | 1 | 「已付款，待收货」 | **确认收货** | 等待买家确认 |
| 交易完成 | 2 | 「交易完成」 | 无 | 无 |
| 已取消 | 3 | 「已取消」+ 取消原因 | 无 | 无 |

**文案铁律**：全站不出现「支付」「付款成功」这类暗示资金经手平台的措辞。买家侧按钮一律写全「**我已完成线下付款**」。

### 5.3 成色档位

`t_product.condition_level`（`TINYINT`）取值：

| code | 展示文案 | 筛选口径 |
|---|---|---|
| 0 | 全新 | ≥ 全新 = 0 |
| 1 | 九成新 | ≥ 九成新 = 0 / 1 |
| 2 | 七成新 | ≥ 七成新 = 0 / 1 / 2 |
| 3 | 五成新及以下 | 全部 |

- **发布页**：单选，必填，默认「九成新」（校园二手最常见的档位，作为数据兜底）
- **列表页**：筛选按「≥ 某档」换算成 `condition_level <= N`
- **详情页**：作为一行标签展示
- **不加索引**：只有 4 个取值、选择性极低，单列索引收益为零 —— 符合「宁可少做」铁律

## 六、联系方式方案（方案 A）

### 6.1 问题

交易动线是「看到商品 → 确认还在吗 / 能便宜吗 / 什么时候在哪见 → 线下见面 → 付款」。项目不做站内聊天，中间这一步必须补，否则买家只能靠「直接下单」赌运气，会产生大量无效订单（商品被锁定、一问发现卖家早卖了）。**这是业务问题，不是体验问题。**

### 6.2 裁定方案

| 方案 | 裁定 |
|---|---|
| **A：详情页暴露联系方式** | ✅ **采用** |
| B：商品留言板（需新表 + 敏感词/举报追问） | ❌ 不做 |
| C：站内 IM（已在 §十五 明确不做） | ❌ 不做 |

### 6.3 交互设计

- 位置：商品详情页 ⑦ 区（卖家卡下方）
- 未登录：按钮显示「登录后查看联系方式」，点击走登录拦截（§2.3）
- 已登录：点击 → 弹出层显示手机号 + 一键复制按钮
- 文案附一句「**手机号同微信**」——避免为微信号再加字段（改表 + 改注册流程，不划算）

### 6.4 两条边界

1. **只在详情页露出，列表页 / 首页绝不露出**（否则列表就变成通讯录）；
2. 手机号**必须登录后可见**——防爬虫批量抓取，同时给「注册」一个真实理由。

### 6.5 后端配合（⚠️ 需后端确认）

`product-service` 查详情时本来就会调 `product → user` 的 `/inner/user/batch`（见 `01-总体设计V1.md` §十）拿卖家昵称头像。只需两处调整：

1. `/inner/user/batch` 的返回 DTO 增加 `phone` 字段；
2. `product-service` 组装详情响应时判断请求头 `X-User-Id`：**为空则把 `phone` 置 null**，非空才透出。

**已查库确认**：`huashui_user.t_user.phone` 为 `varchar(20) NOT NULL UNIQUE` —— 字段已存在且唯一，
**不用新增接口、不用新增字段、不用改表**。

另：`t_user` 中**没有**微信号字段，所以文案统一用「手机号同微信」，不为微信号额外加字段。

### 13.2 为什么不采纳「批量接口返回手机号」

**替代方案（已实现并实测通过）：独立接口 `GET /api/user/{id}/contact`，登录后返回手机号。**

不采纳批量透出的三条理由：

1. **危险的默认值。** 批量接口一旦返回手机号，等于把「全站手机号」变成**任何内部调用方的默认可得数据**。
   现在只有 product 调它，将来 order 也要调（订单页要展示对方联系方式）——那时它顺手就能拿到所有人的手机号，而没人会意识到这是个问题。
2. **无法单独限流。** 若有人爬手机号，你想限流「取手机号」这个行为；但批量接口同时承担「取昵称头像」的正常流量，一限流就误伤。
3. **业务规则错位。** 「谁能看手机号」是**用户域的隐私规则**，放到 product-service 里判断 `X-User-Id` 会形成规则复制，
   将来规则变更（如改成「双方下单后才可见」）要改两个服务。

**实测结果：**

| 场景 | 结果 |
|---|---|
| 游客访问 `/api/user/{id}/contact` | HTTP **401** |
| 登录后访问 | HTTP **200**，返回手机号 |
| `/inner/user/batch` | 返回字段**不含** `phone` |
| 游客访问 `/api/user/detail/{id}`（卖家主页） | HTTP **200**，字段**不含** `phone` |

### 13.3 ⚠️ 关于 `campus`：后端建议仍然新增字段

本文档 §八 的方案是「两级联动拼接进单个 `trade_place`，**不用改表**」，筛选靠 `trade_place LIKE '龙子湖%'`。

**技术上前缀 LIKE 可以走索引，所以这个方案能跑通，但后端仍建议加独立列，原因不是性能：**

- `trade_place` 是**给人看的展示文本**，`campus` 是**给机器筛的维度**。从展示字符串里解析维度，属于把数据塞进展示层；
- 一旦文案调整（例如改成 `龙子湖校区 · 第二食堂`），筛选会**静默失效**——不报错，只是结果不对；
- 加列的代价极小（1 个 `VARCHAR(16)` 列 + 1 个枚举 + 1 个索引），且建表脚本同步即可。

**→ 此项等用户决策，未定前不动表。**（若决定不加列，后端按 `trade_place` 前缀实现，但会在代码里显式注释这个隐患。）

### 13.4 已实现并需前端知晓的跨端约定

| 约定 | 说明 |
|---|---|
| **所有 `Long` 序列化为字符串** | 雪花 ID 是 19 位，超出 JS 安全整数范围（2^53-1，16 位）。实测 `2103749049839185921` 传到前端会变成 `...9185900`，**且不报错**。因此**所有 ID 一律是字符串**，前端不要做数值运算，直接透传即可 |
| **分页计数保持数字** | `PageResult` 的 `total` / `pages` / `current` / `size` 改为 `int`，**序列化后仍是数字**，本文档 §3.1 的示例无需修改。规则统一为：「Long 只用于 ID（转字符串），数量用 int（保持数字）」 |
| 时间格式 | `yyyy-MM-dd HH:mm:ss` 字符串 |
| 已实现接口（实测通过） | `POST /api/user/register`、`POST /api/user/login`、`GET\|PUT /api/user/info`、`PUT /api/user/password`、`GET /api/user/detail/{id}`、`GET /api/user/{id}/contact`、`GET /inner/user/batch` |
| 接口路径差异 ⚠️ | 后端当前用 `GET /api/user/detail/{id}`（而非 `/api/user/{id}`），避免与 `/api/user/info`、`/api/user/password` 产生路径歧义。**前端实现时以 `/detail/{id}` 为准** |
