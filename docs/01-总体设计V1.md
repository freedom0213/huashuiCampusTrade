# 华水校园闲置交易平台 —— 总体设计 V1

> 版本：V1（已确认）
> 范围：4 个微服务 + 1 个公共模块 + 3 个 database + 7 张核心表
> 完成度目标：80% ~ 90%

## 一、项目定位

| 项 | 内容 |
|---|---|
| 名称 | 华水校园闲置交易平台（huashuiCampusTrade） |
| 定位 | 面向华北水利水电大学学生的校内 C2C 闲置物品交易平台 |
| 目标 | ① Java 微服务实践载体 ② 简历项目 ③ 掌握 Spring Boot / Cloud 全链路 |
| 规模上限 | 4 个可部署服务 + 1 个网关 + 3 个库 + 约 8 张表 |

**铁律：宁可少做功能，也不要为「看起来复杂」而无意义地增加微服务和技术。**

## 二、用户角色

| 角色 | 权限 |
|---|---|
| 游客 | 浏览商品列表、商品详情、分类 |
| 学生用户 | 发布商品、收藏、下单、取消订单、上下架自己的商品、查看订单 |
| 管理员 | 商品审核、商品强制下架、用户禁用/启用、分类管理 |

**关键决策：学生用户不区分「买家」和「卖家」。**
校园二手的本质是同一个人兼具两种身份，拆成两张表会立刻产生「身份如何合并」的问题，属于无意义的复杂度。落地方式：`t_user` 单表 + `role` 字段（1 学生 / 2 管理员）。

## 三、核心业务流程

### 3.1 发布 → 审核 → 上架

```
登录 → 填写商品(分类/标题/描述/价格/图片/交易地点) → 提交
   → 状态 = 待审核(PENDING_AUDIT)
   → 管理员审核 ──通过──→ 在售(ON_SALE)
                └─驳回──→ 已驳回(REJECTED)，卖家可改后重提
```

### 3.2 浏览 → 下单 → 完成

```
浏览列表/搜索 → 商品详情 → 收藏 / 下单
   → 创建订单(待支付 WAITING_PAY) + 商品锁定(LOCKED)
   → 买家线下当面付款后点「我已完成付款」→ 已付款(PAID)
   → 商品置为 已售出(SOLD)
   → 买家确认收货 → 交易完成(COMPLETED)
```

### 3.3 超时取消（异步最终一致的关键落点）

```
订单创建 → close_deadline = now + 30min → WAITING_PAY
   → 30 分钟内未付款
   → XXL-JOB 每分钟扫描 → 订单 CANCELLED
   → 发 RabbitMQ 消息 → product-service 消费 → 商品 LOCKED → ON_SALE
```

### 3.4 状态机

**商品**

| 状态 | 值 | 可迁移到 |
|---|---|---|
| 待审核 | PENDING_AUDIT | ON_SALE / REJECTED |
| 在售 | ON_SALE | LOCKED / OFF_SHELF |
| 已锁定 | LOCKED | SOLD（付款）/ ON_SALE（取消或超时） |
| 已售出 | SOLD | — （终态） |
| 已下架 | OFF_SHELF | ON_SALE |
| 已驳回 | REJECTED | PENDING_AUDIT |

**订单**

| 状态 | 值 | 可迁移到 |
|---|---|---|
| 待支付 | WAITING_PAY | PAID / CANCELLED |
| 已付款 | PAID | COMPLETED |
| 交易完成 | COMPLETED | — （终态） |
| 已取消 | CANCELLED | — （终态） |

**规则：商品下架只影响新订单，已创建的订单继续有效**（防止卖家为逃避交易而批量下架）。

## 五、微服务拆分与职责

### 5.1 服务清单

```
huashui-gateway         统一入口
huashui-user-service    用户域
huashui-product-service 商品域
huashui-order-service   交易域
huashui-common          公共模块（非服务，不部署）
```

### 5.2 职责边界

**gateway**
- 路由转发、JWT 签名与过期校验、全局 CORS
- 解析 `userId` / `role` 写入请求头 `X-User-Id`、`X-User-Role` 透传
- 白名单：`/api/user/login`、`/api/user/register`、`/api/product/list`、`/api/product/detail/**`
- **不做**业务校验与细粒度权限判断

**user-service**
- 注册（BCrypt 加密）、登录（签发 JWT）、用户信息查询与修改
- 批量查询接口（供 product-service 查卖家信息，避免 N+1）
- 管理员：用户列表、禁用/启用
- **不做** RBAC 角色权限表（一个 `role` 字段够用）

**product-service**
- 分类、商品、图片、收藏的全部 CRUD
- 商品状态机维护
- 商品审核（管理员）
- 缓存：详情缓存、分类缓存、浏览量累计、热门榜
- 对外提供内部接口：商品快照查询、商品锁定、商品状态变更
- 消费 MQ：订单取消 → 恢复商品在售
- **不做**订单相关逻辑

**order-service**
- 创建订单、订单查询、状态流转、取消、确认收货
- 超时取消的执行逻辑（由 XXL-JOB 触发）
- 发送 MQ 消息、本地消息表、补偿任务
- **不做**商品信息维护，**不做**真实支付

### 5.3 服务调用关系

| # | 方向 | 方式 | 场景 |
|---|---|---|---|
| 1 | 前端 → gateway → 各服务 | HTTP 路由 | 全部外部请求 |
| 2 | order → product | OpenFeign 同步 | 下单：查商品快照 + 锁定商品 |
| 3 | order → product | OpenFeign 同步 | 付款后 `ON_SALE → SOLD` |
| 4 | product → user | OpenFeign 同步（批量） | 列表/详情展示卖家信息 |
| 5 | order → MQ → product | RabbitMQ 异步 | 取消/超时后商品恢复在售 |

**核心判断**

- **「锁定商品」必须同步**：用 MQ 异步锁定会导致用户看到「下单成功」但商品早已被别人买走，这是**假成功**。凡用户当场可感知、影响后续判断的操作，必须同步。
- **「恢复商品上架」可以异步**：取消后商品晚 1 秒回到列表，用户无感，适合丢给 MQ。
- **禁止 `product → order` 反向 Feign 调用**，否则形成循环依赖。

## 六、数据库设计

### 6.1 库划分

同一 MySQL 实例，**3 个独立 database**，每个服务只连自己的库：

| database | 归属服务 |
|---|---|
| `huashui_user` | user-service |
| `huashui_product` | product-service |
| `huashui_order` | order-service |

不选「单库多表」：共用库会让任何表都能被跨服务 JOIN，服务边界会迅速瓦解。
不选「3 个独立 MySQL 实例」：本地开发成本高，收益为零，属于过度设计。

### 6.2 表清单

**huashui_user**

| 表 | 关键字段 | 索引 |
|---|---|---|
| `t_user` | id, username, password(BCrypt), nickname, phone, avatar, student_no, dept, role, status, create_time, update_time, deleted | uk_username, uk_phone, uk_student_no, idx_status |

**huashui_product**

| 表 | 关键字段 | 索引 |
|---|---|---|
| `t_category` | id, name, sort, status | uk_name |
| `t_product` | id, seller_id, category_id, title, description, price, original_price, cover_url, trade_place, view_count, favorite_count, status, reject_reason, publish_time, sold_time, create_time, update_time, deleted | idx_seller_id, idx_category_id_status, idx_status_publish_time, idx_title |
| `t_product_image` | id, product_id, url, sort | idx_product_id |
| `t_favorite` | id, user_id, product_id, create_time | uk_user_product, idx_user_id_create_time |

**huashui_order**

| 表 | 关键字段 | 索引 |
|---|---|---|
| `t_orders` | id, order_no, buyer_id, seller_id, product_id, product_title / product_cover / product_price（快照）, total_amount, status, close_deadline, pay_time, finish_time, cancel_time, cancel_reason, create_time, update_time | uk_order_no, idx_buyer_id_status, idx_seller_id_status, idx_status_close_deadline |
| `t_local_message`（80% 阶段） | id, msg_id, exchange, routing_key, biz_type, biz_id, payload, status, retry_count, next_retry_time, create_time | uk_msg_id |

### 6.3 三个关键设计意图

1. **订单表故意冗余商品标题/封面/价格快照。** 既是业务刚需（成交价快照，卖家事后改价不影响历史订单），也顺带解决跨库查询问题。**规则：订单创建后，快照不再与商品同步。**
2. **不给 `t_product` 加「锁定订单号」字段。** 恢复商品时靠消息携带的 `product_id`，代价是需要一条兜底补偿任务（见 §九）。
3. **主键用雪花 ID**（MyBatis-Plus `ASSIGN_ID`）；`order_no` 用「时间戳 + 随机数」，避免暴露平台真实单量。

### 6.4 通用约定

- 时间统一 `DATETIME` + `LocalDateTime` + 东八区
- **所有删除走逻辑删除**（`deleted` 字段），不做物理删除
- MySQL 账号：`huashui`@`localhost`，只授权到这 3 个库

## 七、Redis 使用场景

| key 模式 | 类型 | TTL | 用途 | 更新策略 |
|---|---|---|---|---|
| `product:detail:{id}` | String(JSON) | 30min + 随机抖动 | 商品详情 | Cache-Aside：先更新 DB，再删 key |
| `product:view:{id}` | String(计数) | 常驻 | 浏览量累加 | `INCR`，XXL-JOB 每 5min 结算回写 |
| `product:dirty:views` | Set | 常驻 | 记录被访问过的商品 id | 配合上一条，避免全库扫描 |
| `product:hot` | ZSET | 常驻 | 热门商品榜 | `ZINCRBY`，定时任务取 TopN |
| `category:list` | String(JSON) | 1h | 分类列表 | 变更时删除 |
| `auth:blacklist:{jti}` | String | 与 token 同期 | 退出登录立即失效（90% 可选） | 登录时校验 |

### 缓存三大问题落点

| 问题 | 场景 | 方案 |
|---|---|---|
| 穿透 | 请求不存在的 `product:99999999` | 缓存空值，TTL 60s。**不用布隆过滤器** |
| 击穿 | 热门商品缓存过期瞬间 | `SETNX` 互斥锁 + **自旋重试**（最多 5 次 / 总超时约 250ms） |
| 雪崩 | 批量 key 同时过期 | TTL 加 0~600s 随机抖动 |

**互斥锁的正确实现（关键在自旋）：**

```
1. 读缓存 → 未命中
2. SETNX lock:product:{id} EX 10 → 尝试加锁
   ├─ 成功 → 查 DB → 写回缓存 → DEL lock → 返回
   └─ 失败 → sleep 50ms → 回到第 1 步重试
3. 重试耗尽 → 降级返回「系统繁忙」
```

**只有第一个请求查 DB**，其余请求自旋等待，缓存写回后立刻命中。**不会造成请求堆积**（堆积是「无自旋」的错误实现才会出现）。

**逻辑过期仅作为面试知识点准备**，不落地（需额外维护异步线程池，属于为面试引入的复杂度）。逻辑过期的正确行为是「**返回旧数据 + 后台异步重建**」，不是「返回失败」。

### 浏览量：避免行锁热点

若每次浏览都 `UPDATE t_product SET view_count = view_count + 1`，高频访问下会变成**行锁热点**。方案：Redis `INCR` 累加 + XXL-JOB 每 5 分钟用 `DECRBY` 取差值结算回 DB，把 N 次写库压缩成 1 次。

## 八、并发下单（本项目最核心的技术点）

**结论：不加显式锁。用数据库条件更新，靠 InnoDB 行锁保证原子性。**

```sql
UPDATE t_product
SET status = 'LOCKED', update_time = NOW()
WHERE id = #{productId} AND status = 'ON_SALE'
```

判断受影响行数：

- `= 1` → 锁定成功，继续创建订单
- `= 0` → 商品已被锁定/已售出 → 返回「商品已被抢购」

**为什么不需要显式加锁？** InnoDB 执行该 UPDATE 时会自动对命中行加**排他行锁（X 锁）**：

```
请求A：拿到行锁 → 执行 UPDATE → status 由 ON_SALE 变 LOCKED → 提交 → 释放锁
请求B：A 持锁期间阻塞等待 → A 提交后拿到锁 → 重新匹配 WHERE → 不匹配
       → 受影响行数 = 0 → 下单失败
```

**不使用 Redis 分布式锁**：本项目并发量远达不到需要它的程度，且会引入「锁超时设多久 / 锁误删 / Redisson 看门狗」等一串必须能答上来的追问。

### 跨服务无事务的风险与兜底

```
① order-service 调 product-service /lock → 商品 LOCKED（product 本地事务提交）
② order-service 创建订单                 （order 本地事务提交）
③ 若第 ② 步失败 → 商品永远锁死
```

- **第一层**：order-service 捕获异常 → 主动调 `/unlock` 补偿
- **第二层（80% 阶段）**：补偿任务扫描「LOCKED 超过 N 分钟且无有效订单」的商品，恢复 `ON_SALE`

### 状态变更必须带前置条件

所有状态流转接口（付款、取消、收货）都必须写 `WHERE status = '<预期前置状态>'`，判断受影响行数。**前端按钮显隐只是体验优化，不是安全边界。**

## 九、RabbitMQ 使用场景

**交换机**：`trade.topic`（topic）

| 队列 | 路由键 | 生产者 | 消费者行为 |
|---|---|---|---|
| `order.cancel.queue` | `order.canceled` | order-service | product-service 消费 → 商品 `LOCKED → ON_SALE` |

**只设计 1 个队列是刻意的判断** —— 与其铺 3 个用不上的队列，不如把 1 个的可靠性做全：

```
Producer Confirm（到交换机）
  → 消息持久化 + 交换机/队列持久化（宕机不丢）
  → Consumer 手动 ACK（消费成功才删）
  → 消费异常 → 重试 N 次 → 死信队列 order.cancel.dlx
  → 消费端幂等（以 order_no 为幂等键）
  → 本地消息表 + 定时补偿（防止「订单已取消但消息没发出去」）
```

### 超时取消方案对比

| | XXL-JOB 扫表 | 延迟队列 TTL+DLX | 延迟插件 |
|---|---|---|---|
| 精度 | 分钟级 | 秒级 | 秒级 |
| 可靠性 | 高（数据在库里，可重跑） | 低（队头阻塞、TTL 不精确） | 高 |
| 实现复杂度 | 低 | 中 | 需装插件 |
| 可观测/可干预 | 强 | 弱 | 中 |
| 风险 | 数据量大时扫描压力 | 消息堆积 | 额外运维 |

**选 XXL-JOB**：订单数据本就在库里，定时任务只是换个姿势查它，不引入新的状态存储。

## 十、OpenFeign 使用场景

| 场景 | 方向 | 接口 |
|---|---|---|
| 商品快照查询 | order → product | `GET /inner/product/{id}` |
| 商品锁定 | order → product | `POST /inner/product/{id}/lock`（返回值表示是否锁定成功） |
| 商品售出 | order → product | `POST /inner/product/{id}/sold` |
| 卖家信息批量查询 | product → user | `GET /inner/user/batch?ids=1,2,3` |

**必须处理的 5 件事**

1. **超时**：connectTimeout 1000ms / readTimeout 2000ms。不配就是默认无限等待，一个慢请求拖垮线程池。
2. **不盲目重试**：`lock` / `sold` 等非幂等接口禁止自动重试。
3. **降级 fallback**：商品服务不可用时下单接口应快速失败，**绝不能伪造成功**。
4. **身份透传**：`RequestInterceptor` 把 `X-User-Id` 带到下游。
5. **内部接口隔离**：`/inner/**` 必须在网关层拒绝外部访问。

## 十一、XXL-JOB 使用场景

| 任务 | 执行器 | 频率 | 逻辑 | 幂等保障 |
|---|---|---|---|---|
| `orderTimeoutCancelJob` | order-service | 每 1 分钟 | 查 `status=WAITING_PAY AND close_deadline < now()`，分批 200，逐单取消并投递 MQ | 条件更新，影响行数=1 才发消息 |
| `viewCountFlushJob` | product-service | 每 5 分钟 | 遍历 `product:dirty:views`，把 Redis 计数差值结算到 DB | 用 `DECRBY` 取走差值 |
| `hotProductRefreshJob` | product-service | 每 10 分钟 | 按 ZSET 取 Top20 | 整体覆盖写 |
| `pendingAuditRemindJob` | product-service | 每 30 分钟 | 统计超 24h 未审商品 | 只读 |

**配置要点**：阻塞处理策略用**丢弃后续调度**（防止上一轮没跑完下一轮又进来），失败重试 0 次（交给下一轮自然重试）。

## 十二、Sentinel 使用场景

| 资源 | 规则 | 目的 |
|---|---|---|
| `/api/product/detail/{id}` | QPS 限流 | 防热 key 被刷 |
| `/api/user/login` | QPS 限流 | 防暴力破解 |
| `order → product` Feign 调用 | 熔断 + 降级 | 商品服务故障时快速失败 |

**降级策略必须区分场景**

- 下单/锁定商品 → **快速失败**，绝不降级成「假装成功」
- 商品详情/列表 → 可返回缓存旧数据
- 分类列表 → 可返回本地兜底常量

## 十四、业务口径（已冻结）

| 项 | 结论 |
|---|---|
| 浏览范围 | 不限制，游客可看 |
| 注册方式 | 用户名 + 密码 + 手机号（唯一性校验，不发验证码） |
| 购买 | 注册即可，不做额外地域/身份校验 |
| 交易方式 | **仅支持校内当面自提**，`trade_place` 必填 |
| 配送 | **不做**（会连锁引入地址簿 / 运费 / 物流 / 退换货 / 纠纷，复杂度失控） |
| 支付 | **模拟支付，资金不经手平台**。按钮语义为「确认已线下付款」 |
| 图片存储 | 本地磁盘 + `FileStorage` 接口抽象（便于切 OSS） |
| 订单超时 | 配置项 `trade.order.timeout-minutes`，默认 30，演示时改 1 |

**「商家支付后标注在哪现场取货」这个设计已落地**：`trade_place` 是商品字段，发布时填写，下单前买家即可看到。平台不需要为「外地用户来不了」写任何限制代码 —— 他看到地点自然会自己判断。

**不做真实支付的三条硬约束**：① 商户号需营业执照，个人无法接入 ② 资金池涉及清算/对账/监管 ③ 接支付就必须接退款与对账，复杂度失控。
**面试口径**：「平台定位为信息撮合，不介入资金流」，并说明预留了 `PayService` 抽象便于将来接入。

## 十五、明确不做（防止需求蔓延）

购物车（孤品逻辑不成立）、真实支付/钱包/退款、**Seata 分布式事务框架**、ES/推荐算法、秒杀压测、Redis 集群/分库分表/多级缓存、短信服务、第三方登录、评价体系、微信小程序/App。

发现值得做的扩展 → **先提出并等确认，绝不擅自加入**。

## 十六、开发路线

| 阶段 | 内容 | 验收方式 |
|---|---|---|
| 0 | 总体设计 V1 | 已完成 |
| 1 | Maven 父工程 + `huashui-common` | `mvn clean install` 通过，common 被依赖 |
| 2 | 基础设施 + 建库建表 | 容器 `docker ps` 正常；Nacos 控制台可访问 |
| 3 | gateway | Nacos 能查到实例；白名单直通；假 token 被拦截 |
| 4 | user-service | 注册登录跑通，拿到可解析的 token |
| 5 | product-service | 发布商品 → DB 有数据；列表/详情正确 |
| 6 | 前端最小闭环 | 浏览器完成「登录→浏览→下单」 |
| 7 | order-service | 下单后商品 LOCKED；取消后恢复 ON_SALE |
| 8 | 收藏 + Redis 缓存体系 | 缓存可观察；并发下单只有一单成功 |
| 9 | RabbitMQ 可靠性 | 停掉 product-service 再恢复，商品最终回到 ON_SALE |
| 10 | XXL-JOB | 把 `close_deadline` 改成过去时间，1 分钟后订单被取消 |
| 11 | Sentinel | 压测触发限流；停掉 product-service 验证快速失败 |
| 12 | 商品审核 + 管理端 | 管理员可审核；驳回商品不能下单 |
| 13 | Docker 全量部署 + 文档 | 一条 `docker compose up` 起全栈 |

**每一阶段流程**：先给设计方案 → 等确认 → 实现 → 验证 → 汇报（做了什么 / 改了哪些文件 / 为什么这样设计 / 如何验证 / 下一步建议）→ 停下等指令。**禁止一次跨多个阶段。**

## 十七、已知限制（面试需主动说明）

| # | 限制 | 说明 |
|---|---|---|
| 1 | 无真实支付 | 有意取舍，见 §十四 |
| 2 | 搜索能力弱 | `LIKE '%kw%'` 走不了索引；数据量上来后应引入 ES |
| 3 | 网关信任 `X-User-Id` | 前提是服务端口不对外暴露；本地开发时存在伪造风险，Docker 部署时用内部网络弥补 |
| 4 | 「僵尸锁定」风险 | 商品 LOCKED 但消息丢失 → 靠补偿任务兜底 |
| 5 | 浏览量可能丢失 | Redis 宕机会丢掉未回写的增量，业务上可接受 |
| 6 | Nacos 单机模式 | 生产需集群 |
